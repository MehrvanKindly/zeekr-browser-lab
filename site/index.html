How the four boundaries apply to installation
JavaScript → native
Bridge names do not reveal a documented installer API. The lab records them without guessing or invoking native methods.
Links / intents
The download and APK intent routes request standard user-visible handling. Installation still depends on Android and the hosting app.
Browser engine
Environment and isolation checks provide context. They do not exploit engine bugs to install software.
File boundary
A Downloads or Files app may pass the downloaded APK to an installer with a readable content URI. A hosted webpage cannot grant that access itself.

If a route is blocked or the device has no installer, record that outcome. These routes do not bypass restrictions or install silently.

READ THE RESULT CORRECTLY

Investigation targets.
Not findings about your car.

This lab does not identify the EU 7X’s browser implementation. A WebView-looking user agent can be changed or reduced; it does not verify the app’s engine, build, configuration or Android security patch level.

Android’s documented risk classes include exposed native bridges, unsafe URI handling and permissive file access. Engine memory-safety bugs require an applicable vulnerable build. Testing their exploitability needs a controlled lab and a verified vendor build.

There is no standard webpage command to enable ADB, silently install an APK or root a vehicle. The Brave section requests downloads and app handoffs; Android owns installation prompts. Additional tests include one explicitly scheduled Brave launch and a notification-permission request. Settings links only request a screen. The lab does not enable ADB, change Android settings, invoke unknown native methods, control the vehicle or exploit the browser.
